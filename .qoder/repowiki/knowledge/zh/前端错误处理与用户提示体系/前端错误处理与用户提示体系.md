本仓库采用「统一请求拦截 + 错误码映射 + 全局消息插件」的前端错误处理模式，围绕 HTTP 层集中处理后端返回的业务错误、网络异常与认证失效，并通过 plugins/modal.js 与 utils/common.js 提供统一的 Toast/Modal/Loading 展示能力。

## 1. 使用的系统与模式
- HTTP 层集中处理：utils/request.js 基于 uni.request 封装 Promise 请求，在 .then 中解析后端响应体 data.code，在 .catch 中捕获网络/超时等底层错误。
- 错误码映射表：utils/errorCode.js 维护 401/403/404/default 等状态码到中文提示的映射，作为默认文案来源。
- 全局消息插件：plugins/modal.js 暴露 $modal.msg / msgError / msgSuccess / alert / confirm / loading / closeLoading 等方法，统一调用 uni.showToast/showModal/showLoading/hideToast/hideLoading。
- 通用工具函数：utils/common.js 导出 toast()、showConfirm()、chooseLocation() 等轻量方法，供非插件场景直接调用。

## 2. 核心文件与职责
- utils/request.js：请求拦截器，负责鉴权头注入、401 自动重登（含微信环境特殊分支）、500/非 200 业务错误提示与拒绝。
- utils/errorCode.js：错误码 → 中文消息字典。
- plugins/modal.js：挂载为 Vue 全局 $modal，封装所有用户可见的错误/成功/确认弹窗。
- utils/common.js：toast、showConfirm、chooseLocation 等无依赖工具函数。
- mixins/pagination.js：分页 mixin 中对 loadData 未实现抛错，并对异步加载失败 catch 后 toast 提示。
- store/modules/user.js：Vuex action 中大量使用 .catch(error => ...) 吞掉或转发错误，不向上抛出。

## 3. 架构与约定
- 错误传播路径：API 模块（api/**/*.js）→ request.js 拦截 → 根据 code 决定 resolve(res.data) 还是 reject(msg/code)；页面/组件通过 Promise .catch 或 async/await try/catch 消费。
- 401 自动登录：非登录接口收到 401 时，尝试触发 WxLogin 重新获取 token 并重试原请求；失败则 LogOut 后 uni.reLaunch('/pages/login')。
- 静默错误：code === 20001（微信未绑定账号）不弹 toast，仅 reject(code)，由调用方自行处理。
- 网络错误归一化：将 Network Error、包含 timeout、Request failed with status code 的消息统一改写为友好中文后再 toast。
- 无中间件机制：项目基于 uni-app 小程序运行时，不存在服务端意义上的「错误中间件」，所有错误处理集中在客户端 request 封装与 UI 层。

## 4. 开发者应遵循的规则
- 不要绕过 request：新增 API 一律通过 import request from '@/utils/request' 发起，避免直接使用 uni.request，以确保错误被统一拦截。
- 区分业务码与网络码：在 .catch 中判断 reject 值是字符串（如 '无效的会话...'、'后端接口连接异常'）还是数字（如 20001），分别做不同处理。
- 优先使用 $modal：需要向用户展示错误时使用 $modal.msgError 或 $modal.alert，而非直接调用 uni.showToast，保证风格一致。
- 401 不再手动跳转：不要在业务代码里自行处理 401，交由 request 自动重登/跳转登录页。
- 谨慎吞掉错误：Vuex action 中的 .catch 已存在大量空 catch，新增逻辑应避免静默吞错，至少保留日志或提示。
- 自定义错误码需同步更新 errorCode.js：若后端新增业务码，需在 errorCode.js 补充映射，否则将回退到 default 文案。
